# T6 ピッチ検出（(f)）YIN と MPM

**話し声の測定は合成音声で代用**（基準音声が無いため）。合成音声（`synthVoice`）は基本周波数の軌跡が式で分かっている（140 + 35·sin(2π·0.23t) + 2·sin(2π·5t) Hz）ので、正解との誤差も出した。生の値は `06-pitch*.csv`、条件は `06-pitch*-run.txt`。

## 実装と条件

- 2 方式とも自前実装（外部のコードは取り込んでいない）。`src/p0_pitch.h`。
  - **YIN**: 差分関数 → 累積平均正規化差分（CMNDF）→ 絶対しきい値 0.15 → 放物線補間。しきい値を下回る谷が無ければ無声。
  - **MPM**（McLeod 法）: 正規化二乗差分関数（NSDF、窓の重なりが減っていく type-II の自己相関）→ 正の区間ごとの最大（key maxima）→ 最大値の 0.93 倍以上の最初のもの → 放物線補間。最大の NSDF が 0.6 未満なら無声。
  - 相関はどちらも FFT で計算（`juce::dsp::FFT`、4096 点）。同じ解析バッファ（最新の N サンプル）を見るので、遅延と CPU の差はアルゴリズムの差だけ。
- 48 kHz、モノラル。ブロックごと（ホップ 128 サンプル = 2.667 ms）に、最新の N サンプルで 1 回検出する。
- 設定は 2 通り:
  - **標準**: 検出範囲 60〜1000 Hz（仕様 §5.7 の [暫定] 値）、積分 1024、N = 1825 サンプル（38.021 ms）
  - **短い窓**: 80〜1000 Hz、積分 512、N = 1113 サンプル（23.188 ms）。`--fmin 80 --integration 512 --tag short`
- 合成の周期波形: 正弦波と、同じ基本周波数に第 2〜第 5 倍音（振幅 1/k）を足した波形。100、150、200、300、400 Hz。0.5 秒の無音 → 1.5 秒の音 → +4 半音（×1.2599）へ位相を保って切り替えて 1 秒。
- **検出遅延**の定義: 変化（音の始まり、または +4 半音の切り替え）のあと、正解の ±10 セントに入り、その後 2 フレーム続けて入っている最初のフレームの、最新サンプルの時刻 − 変化の時刻。ホップ（2.667 ms）の刻みを含む。
- **定常の誤差**: 解析バッファ全体が 1 つの定常な音に入っているフレーム（変化から 100 ms 以降）の平均と最大。

## 結果: CPU

条件: 合成音声 30 秒（10 秒を 3 周）をホップ 128 で検出、1 回の `detect()` の時間（`QueryPerformanceCounter`）。CPU % は「オーディオのブロックごとに 1 回検出する」として、1 回の時間 ÷ バッファ時間。計測スレッドは MMCSS「Pro Audio」。依頼者のゲームと Discord が動いている状態（PC 全体のビジー率 70.2 %（標準）/ 65.3 %（短い窓））。

| 設定 | 方式 | 1 回の時間 p50 / p99 / 最大 (µs) | 回数 | バッファ 128 ごと p50 / p99 (%) | 256 ごと p99 (%) | 480 ごと p99 (%) |
|---|---|---|---|---|---|---|
| 標準 | YIN | 290.500 / 581.100 / 2545.700 | 11236 | 10.894 / 21.791 | 10.896 | 5.811 |
| 標準 | MPM | 197.100 / 391.700 / 2218.200 | 11236 | 7.391 / 14.689 | 7.344 | 3.917 |
| 短い窓 | YIN | 273.300 / 572.100 / 2509.300 | 11242 | 10.249 / 21.454 | 10.727 | 5.721 |
| 短い窓 | MPM | 177.900 / 345.200 / 2450.500 | 11242 | 6.671 / 12.945 | 6.472 | 3.452 |

どちらも FFT は 4096 点（MPM は 2N 以上が要る）。YIN は短い窓なら 2048 点で足りる（N + 積分 = 1625）が、比較をそろえるため 4096 のままにした。最初に通常の優先度で測った値（ゲーム実行中）は p99 が YIN 2714.900 µs、MPM 1953.900 µs で、優先度で大きく変わる。

## 判定（仕様 §13.1 の目安: 検出遅延 25 ms 以内、定常な母音で ±10 セント以内、CPU 5 % 以内。暫定）

CPU は「10 ms（480 サンプル）に 1 回検出する」ときの p99 で判定した（バッファ 128 で毎ブロック検出すると、どちらも 5 % を超える）。

| 設定 | 方式 | 検出遅延（立ち上がり / 切り替え、全条件の最大） | 定常の誤差（最大） | CPU（480 ごと p99） | 目安 |
|---|---|---|---|---|---|
| 標準（60〜1000 Hz） | YIN | 39.354 / 38.021 ms → 不合格 | 0.094 セント → 合格 | 5.811 % → 不合格 | 不合格 |
| 標準（60〜1000 Hz） | MPM | 20.688 / 38.021 ms → 切り替えが不合格 | 0.019 セント → 合格 | 3.917 % → 合格 | 切り替えの遅延だけ不合格 |
| 短い窓（80〜1000 Hz） | YIN | 24.521 / 23.188 ms → 合格 | 0.126 セント → 合格 | 5.721 % → 不合格 | CPU だけ不合格 |
| 短い窓（80〜1000 Hz） | MPM | 24.521 / 23.188 ms → 合格 | 0.038 セント → 合格 | 3.452 % → 合格 | **合格** |

**MPM のほうが良い**: 同じ解析バッファで、1 回の時間が 32 % 短い（p50 197.100 µs 対 290.500 µs、標準）、音の立ち上がりの検出が速い（標準で 4.688〜20.688 ms 対 26.021〜39.354 ms）、合成音声で有声と判定する割合が高い（0.9259 対 0.8252）、正解との誤差の中央値が小さい（2.139 対 3.133 セント）。弱点は外れ（p99 61.263 対 32.640 セント、オクターブ近くのずれが少し混じる）で、使う側（オートピッチ、スケール連動）で外れを捨てる処理が要る。


## TTS 代用での測り直し（2026-10-03、参考）

**入力は TTS の読み上げ（`testdata/tts-speech.wav`、Windows の「Microsoft Haruka Desktop」）で、依頼者本人の声ではない。** 上の表（合成音声）はそのまま残す。

- ファイル: `06-pitch-tts*.csv`、`06-pitch-tts-run.txt`、`06-pitch-short-tts*.csv`、`06-pitch-short-tts-run.txt`（`p0_pitch --input <tts> --tag tts`、`p0_pitch --fmin 80 --integration 512 --input <tts> --tag short-tts`）
- 周期波形の表（`06-pitch-tts.csv`）は合成の正弦波・倍音なので前回と同じ値。CPU の表も `p0_pitch` は合成音声で測る作りなので、差は PC の混み具合だけ（今回のビジー率 18.8 %、前回 70.2 %。標準の MPM の p99 は 391.700 → 244.300 µs）
- **TTS には正解の f0 が無いので、正解との誤差は出せない**。出せるのは有声と判定した割合と、隣のフレームとの差だけ

| 設定 | 方式 | 有声の割合（合成音声 → TTS） | 隣のフレームとの差の中央値（セント、合成音声 → TTS） |
|---|---|---|---|
| 標準 | YIN | 0.8252 → 0.6777 | 1.171 → 4.656 |
| 標準 | MPM | 0.9259 → 0.7570 | 1.177 → 4.175 |
| 短い窓 | YIN | 0.8501 → 0.6729 | 1.238 → 5.665 |
| 短い窓 | MPM | 0.9236 → 0.7338 | 1.331 → 5.310 |

- 有声の割合が下がるのは、実際の読み上げには無声の子音や息の区間があるため（合成音声はほぼ全部が有声）で、検出の失敗とは限らない。TTS でも **MPM のほうが有声と判定する割合が高く、隣のフレームとの差も小さい**ので、MPM を選んだ判断は変わらない。短い窓（80 Hz〜）は隣との差が少し増える（4.2 → 5.3 セント）
- 本人の声での確認（特に低い声の 80 Hz 付近、オクターブの外れ）は基準音声の録音待ち
