## 結論（判断材料）

**推奨する ShifterConfig: `blockSamples = 1440`（30 ms）、`intervalSamples = 480`（10 ms）、`splitComputation = false`。**

| 項目 | 値（推奨設定） | 基準 | 判定 |
|---|---|---|---|
| 遅延（報告値 = 実測値） | 1440 サンプル = **30.000 ms** | 変換に使えるのは 10〜20 ms（下の予算。60 ms 目標）/ 〜50 ms（上限 100 ms） | 60 ms 目標は**不合格**、上限 100 ms は合格 |
| CPU（3 インスタンス、MMCSS、バッファ 480） | p50 2.360〜3.511 %、**p99 3.878〜9.249 %**、最大 25.004 % | A-6: 25 % 以下（A-14 により既定のバッファ 480 で判定。p99 で見た） | 合格 |
| CPU（同、バッファ 128 / 256） | p99 15.765 % / 11.244 %（4 組の最悪） | 同上 | 合格 |
| 音量差（4 組） | 0/0: -0.000 dB、4/2.5: -2.811、-4/-2.5: -2.021、-9/-5: -3.323 dB | ±2 dB（T2）/ ±1 dB（F-02-12） | 0/0 以外は**不合格**（どの設定でも同じ。下の「音量差」） |
| AC-04（220 Hz の正弦波） | +12 st → 439.9386 Hz（**-0.242 セント**）、フォルマントだけ ±6 st → 220 Hz（最大 0.017 セント） | ±10 セント | 合格 |

理由:

1. **遅延の目標 60 ms に入る設定は、ブロック 20 ms（960）だけ**。ところが 960 は AC-04 に落ち（+12 st で +24.592〜+50.515 セント）、100〜400 Hz の音程の正確さも悪い（960 / 120 では倍音つきの波形で ±10 セント以内が 27 組中 9 組、100 Hz 付近では出力の周期が崩れる組がある）。低い声（男声 100 Hz 前後）は 20 ms のブロックに 2 周期しか入らない。20 ms で行くかは試聴で決めるべきで、測定の数字だけでは推せない。
2. 30 ms（1440）の中では、**interval 480 が CPU 最小**（バッファ 480 では、毎回ちょうど 1 回だけスペクトルを計算するので負荷が平らになる）で、AC-04 にも合格する。いまの既定値（1440 / 240）は CPU が約 2 倍（p50 4.713〜6.664 %）で、AC-04 に落ちる（+23.020 セント）。
3. `splitComputation` は音を変えない（音量差・音程の数値が split なしと完全に同じ）。遅延が interval ぶん増え（480 なら +10 ms）、バッファ 480 では得が無い（もともと毎回 1 回の計算）ので、**なし**。バッファを 128 / 256 にする場合だけ、p99 を下げる効果がある（例: 960 / 240 のバッファ 128 で p99 12.169 % → split で 8.422 %）。

注意: interval 480 は重なりが 3 倍（block / interval = 3）で、いまの既定値（6 倍）より粗い。試聴で「ざらつき」が目立つなら、次点は **1440 / 360**（30 ms、AC-04 +1.702 セント、CPU p99 8.243〜14.556 %）。60 ms 目標を守るなら 960 / 240（20 ms、CPU p99 5.412〜9.350 %）だが、音程の正確さを捨てることになる。

**全体の遅延の見込み（推奨設定、バッファ 480）: 入力 10 + ノイズ抑制 20.000 + 変換 30.000 + 出力と仮想ケーブル 10〜20 = 70〜80 ms**（入力・出力・ケーブルは未測定。§5.4 の目安の値）。60 ms 目標は届かず、上限 100 ms には入る。§5.5 の決め方（A で満たせなければ B、それでも届かなければ目標を見直す）に従うと、目標の見直し（Q6）か、B（自前実装）の検討になる。

## 測定条件

- Release ビルド、48 kHz、モノラル、float32。`p0_shifters --cpu-seconds 10`（2026-10-03 01:47:39 終了、約 6 分）。条件の全文は `02-shifters-run.txt`。
- 遅延: 報告値 = `inputLatency() + outputLatency()`。実測は指示書の方法（入力と出力の 1 ms 刻み RMS 包絡の相互相関、0〜300 ms）と、0/0 のときは波形の相互相関（包絡のずれ ±96 サンプルを探索）。
- 音量差: 出力の RMS − 入力の RMS（dB）。1 秒目から入力の終わりまで、遅延を補正（presets §5.1 の測り方）。
- CPU: 3 インスタンス（シード 1, 2, 3、同じパラメータ）を 1 ブロックごとに順に処理した時間 ÷ バッファ時間（%）。`QueryPerformanceCounter`。入力 10 秒を 1 周、最初の 0.5 秒を除く。**計測スレッドは MMCSS「Pro Audio」**（JUCE の WASAPI の音声スレッドと同じ扱い。`AvSetMmThreadCharacteristicsW` は成功）。
- PC の状態: **依頼者がゲーム（AceCombat8）と Discord を動かしていた**。測定区間ごとの PC 全体のビジー率は表の列（58.1〜99.9 %）。静かな PC の値ではない。
- ピッチとフォルマントの設定: `setTransposeSemitones (p)`、`setFormantSemitones (f, compensatePitch = true)`、`setFormantBase (0)`（ライブラリ既定の自動推定）。`compensatePitch = true` は、ピッチを動かしてもフォルマントが動かないようにするため（F-02-2 の「独立」）。

### API の確認（`third_party/signalsmith-stretch/signalsmith-stretch.h` から）

- `presetDefault (nChannels, sampleRate, splitComputation = false)` = `configure (nChannels, sampleRate*0.12, sampleRate*0.03, split)` → 48 kHz で 5760 / 1440
- `presetCheaper (nChannels, sampleRate, splitComputation = true)` = `configure (nChannels, sampleRate*0.1, sampleRate*0.04, split)` → 4800 / 1920、split あり
- `inputLatency()` = `stft.analysisLatency()` = `blockSamples − analysisOffset`、`outputLatency()` = `stft.synthesisLatency() + splitComputation*interval`。対称の Kaiser 窓で offset = block / 2 なので、合計は block（split なら + interval）
- `setFormantSemitones (semitones, compensatePitch = false)`、`setFormantBase (baseFreq = 0)`（コメント: 「Rough guesstimate of the fundamental frequency, used for formant analysis. 0 means attempting to detect the pitch」。周波数はサンプルレートに対する比）
- ヘッダの `version` は {1, 3, 2}（`third_party/CMakeLists.txt` のコメントは 1.4.0）

## 音量差の原因（フォルマント処理）

`02-level-scan.csv`（ピッチ -12〜+12 × フォルマント -6〜+6 の 55 組、`compensatePitch` あり/なし）から:

- **ピッチだけを動かし、フォルマントの処理を止める**（`compensatePitch = false`、フォルマント 0）と、音量差は -0.090〜-1.028 dB で、ほぼ ±1 dB に入る。
- フォルマントの処理が働くとき（`compensatePitch = true` でピッチ ≠ 0、またはフォルマント ≠ 0）に、-0.372〜-9.391 dB 下がる（14 設定の範囲）。たとえば推奨設定のフォルマントだけ（ピッチ 0）で -0.972〜-3.642 dB、ピッチだけ（補正あり）で -0.897〜-6.111 dB。
- つまり目減りは Signalsmith の**フォルマント包絡の補正**から来ている。合成音声はフォルマントの山が鋭い（帯域通過の Q 6〜10）ので、実際の声では量が違う可能性がある。基準音声で測り直すこと。
- F-02-12（全範囲で ±1 dB）は、ライブラリだけではどの設定でも満たせない（55 組中 ±1 dB 以内は 6〜14 組）。
