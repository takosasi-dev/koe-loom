# T5 変換器の並列処理（(h)、F-15-1）

**入力は合成音声で代用**（`synthVoice` 10 秒を繰り返す。基準音声が無いため）。生の値は `05-parallel*.csv`、条件は `05-parallel*-run.txt`。

## 作ったもの（`p0_parallel`）

- 変換器: Signalsmith Stretch を 3 インスタンス（本声 4 / 2.5、レイヤー 1 が -4 / -2.5、レイヤー 2 が -9 / -5。ピッチ st / フォルマント st）。シード固定。
- **実時間と同じ周期**: 専用のスレッドが、次のブロックの期限まで待ってから処理を始める。`timeBeginPeriod (1)`（成功）＋高分解能の待機タイマー（`CREATE_WAITABLE_TIMER_HIGH_RESOLUTION`）で期限の約 200 µs 前まで寝て、残りは空回しで待つ。オーディオデバイスは開かない。
- `single`: 周期のスレッドが本声 → レイヤー 1 → レイヤー 2 を順に処理し、足す。
- `parallel`: ワーカースレッドを 2 本作り、周期のスレッドが本声を処理し、レイヤー 2 つをワーカーに渡す。合図はアトミック変数（世代の番号）。待つ側は約 50 µs 繰り返し確認したあと `WaitOnAddress` に移り、渡す側は `WakeByAddressSingle`。足す順序は固定（本声、レイヤー 1、レイヤー 2）。ワーカーがバッファ時間の 50 % の期限に間に合わなければ、そのブロックのそのレイヤーを無音にして数える（F-15-4）。ワーカーがまだ前のブロックを処理中なら、そのレイヤーは飛ばして数える。
- **MMCSS「Pro Audio」**（`AvSetMmThreadCharacteristicsW`）: 周期のスレッドとワーカー 2 本の全部に付けた。**全条件で成功**（`std::thread` で作ったワーカーにも付けられる。§5.9 の [未確認]「JUCE でそのまま使えるか」に対しては、Win32 の API を直接呼べば付けられることを確認）。
- 期限切れ: 1 ブロックの処理時間（ブロックの開始 → 足し終わり、壁時計）がバッファ時間を超えた回数。両モード同じ定義。
- ワーカーの起床遅延: 合図を出す直前の時刻から、ワーカーが処理を始めるまで。
- プロセス全体の CPU 時間: `GetProcessTimes`（指示書どおり。時計の割り込みごとにしか増えない）と、`QueryProcessCycleTime`（サイクル単位で正確）の両方。周期のスレッドの空回し（約 200 µs/ブロック）も含む。
- **F-15-3 の確認**: 周期をとらずに 2000 ブロック、`single` と `parallel` の出力を 1 サンプルずつ `memcmp` で比べた。**全バッファ・全設定で一致**。

考えておくこと:
- 推奨設定では、**1 スレッドでもバッファ 480 の p99 は 7.729 %** で、A-6 の 25 % の 3 分の 1 以下。並列にしなくても予算に入る。並列の利点は、重いエフェクト（Phase 5）やレイヤーを足したときの余裕。
- 並列にするとプロセス全体の CPU は増える（+31.786〜+89.421 %。待ちの空回しのぶん）。§5.9 の注意どおりで、タスクマネージャーの CPU 使用率は上がる。
- ワーカーの起床遅延は p99 で 39.200〜121.200 µs。最大はバッファ 128 で 950.600 µs（期限 = バッファ時間の 50 % = 1333.333 µs）、480 で 1613.500 µs（期限 5000 µs）で、起床だけで期限を超えたことはなかった。ただしバッファ 128 では最大が期限の 71 % まで来ていて、ゲームで混んでいると余裕は小さい。
